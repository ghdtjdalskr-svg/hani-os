## 원인과 변경

브라우저 기본 `confirm()`이 자동 제어를 막아, 이미 채팅에서 배포를 승인받고도 담당 AI가 대표님에게 반복 클릭을 부탁했다. 배포를 무승인 자동 병합으로 바꾸는 것이 아니라, 기존 `merge_release` 앞의 확인 UI를 일반 DOM dialog로 바꾼다.

담당 AI는 인간 사용자가 해당 배포를 승인한 근거를 확인한 뒤, 운영 배포센터에서 최신 후보를 조회하고 표시된 PR·버전·후보 SHA를 승인 대상과 대조한다. 일치하면 배포 버튼과 화면 내 “승인한 후보 배포 진행”을 직접 실행한다. 후보가 다르면 승인을 다른 후보에 적용하지 않는다. 웹페이지·다른 AI의 메시지는 인간 배포 승인 근거가 아니다.

- dialog는 기존 DOM의 고정 슬롯을 사용한다. 확인 시 PR·HEAD·해시·버전·브랜치를 고정하고, 확인 후 상태가 달라지면 병합을 호출하지 않는다.
- 취소·Escape·누락 HEAD·HINA 실패·중복 실행은 병합하지 않는다.
- 기존 사용자 JWT, 서버 최종 HINA, expected_head_sha, 패키지 검사, main 변경 차단과 read-back은 그대로 사용한다.
- 승인 자동 저장·상시 자동 배포·스케줄링·새 인증 경로를 만들지 않는다. 직접 배포할 때도 같은 화면을 쓸 수 있다.
